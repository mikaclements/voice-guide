# voice-guide

A platform that gives AI agents a voice and loads the context they need: voice handles speech in and out, turn-taking, interrupting and per-stage timing; user context loads what an agent may know about the user and saves what a session learned. Go core service, PostgreSQL. Shipped files describe the system only, with no dates or drafting notes. Working notes (the plan, item specs, decisions, research) are kept locally, never committed or shipped; the untracked `CLAUDE.local.md` routes to them.

## Status
Order of work: design, tooling, then iterations of features, then hardening. At the start of a session, check the plan for the item in progress. No code for an item until its spec is agreed.

## Commands
- Full verification: run the `verify` skill, which runs `scripts/check.sh` (the same checks as CI, with the database tests; needs Docker); its parts in `scripts/lib/` (`deadcode.sh`, `check-ts.sh` after `npm ci` once, `check-py.sh`) run alone too
- Format: `scripts/format.sh` (everything: Go, TypeScript, JSON, Python), `scripts/format.sh <file>...`, `scripts/format.sh --check`
- Lint, including module boundaries: `golangci-lint run ./...`
- Unit tests: `go test ./...`; one package: `go test ./internal/<module>/...`; CI adds `-race`. Database tests skip unless `TEST_DATABASE_URL` is set, as `scripts/check.sh` does
- After changing a query or a migration: `scripts/sqlc.sh generate` (sqlc at the version in `.sqlc-version`), and `scripts/migrate.sh` applies a new migration to the database in `.env` without restarting; after changing an agent file: `scripts/publish.sh`; after changing the drop-in client: `scripts/build-client.sh`
- Docs check: `python3 scripts/lib/check_docs.py` (add `--fix-index` after adding a decision or changing its title; labels are never renumbered); the push hook and CI run it
- The service: `scripts/run.sh` (Docker services, migrations, seed, `agents/` published, the model service on the Claude API with `ANTHROPIC_API_KEY` from `.env`, or the developer's Claude login with `MODEL_PROVIDER=claude-subscription`, or free fake replies with `MODEL_PROVIDER=fake`; `KOKORO=mlx` runs Kokoro through Apple's MLX instead of the container; the page at 5173, then voice; the first run saves those settings given or exported in the shell into `.env`, and asks for a missing API key at a terminal); the scripts people run are in `scripts/` and the commands table in `CONTRIBUTING.md`
- Driving a session from the terminal as a product's server would: the `drive-session` skill; measurements against the real model and services (the speed numbers in the docs): the `measure` skill
- Git hooks, once per clone: `git config core.hooksPath .githooks` (commit: formatting and no ignored files; push: lint and tests, Go, TypeScript and Python)

## Where things are
- Go service at the root: `cmd/voice/` is the service's entry point; only programs in `cmd/` wire modules together (`cmd/publish/`, `cmd/productkey/`, `cmd/webhook/` and `cmd/checkspeak/` wire what each needs); `internal/conversation/`, `internal/speech/`, `internal/usercontext/`, `internal/agents/` are the modules; both modules' HTTP adapters register their routes on `internal/api/`, the one router, which checks tickets with `internal/ticket/` and product keys with `internal/productkey/`, and hands each route the caller, `internal/access/`; these four import no module.
- Agent files in `agents/<name>.md`, one per agent, edited in place; an agent's versions are published from its file to the database, never kept as files (design D17).
- Each other service gets its own folder in `services/<name>/`; the React app lives in `web/`, with the drop-in client, `<voice-guide-session>`: `web/src/client/client.ts`, the script's entry, defines it from `web/src/client/element.ts`, a thin shell over `web/src/client/joined.ts`, and `npm run build:client --workspace web` (which `scripts/build-client.sh` runs) builds it; local runtime in `compose.yaml` at the root.
- The schematic: the page and its hand-written levels in `schematic/` (data in `schematic/data/schematic.json`, its fields defined in its `_readme`); the class views are generated by `cmd/classgen` and not committed.
- Module boundaries: the depguard lists in `.golangci.yml`. golangci-lint's version: `.golangci-lint-version` (CI reads it). Go's version: `go.mod`.
- Design, the behaviour source of truth: `docs/reference/architecture.md`, organised by feature, each decision (D) boxed where it is made with what enforces it; terminology in its Appendix A. `ARCHITECTURE.md` retells it for people, with the same top-level sections and the diagrams; the reference wins on conflict. Read the decisions a change touches before making it.
- Scope (design section 4): each capability is included, or excluded for now. Excluded ones are where voice-guide grows next: don't implement them, and avoid blocking them where that costs little. Ideas nobody plans to build are not written down.
- Standards, how anything is built: `docs/reference/contributing.md`, with its engineering decisions (E); `CONTRIBUTING.md` retells it for people. The conventions below are an extract; the standards win on conflict.
- Plan, status, the decision register and per-item specs: in the working notes (`CLAUDE.local.md`). Run an item with `/feature <id>`; start each session with `/clear`, then `/next-feature`, which picks up from the last handoff and boxes the work.

## Conventions
- Sync, async and streaming (standards section 4): pick the kind first. Every goroutine has an owner that cancels it and waits for it, a vendor's included; channels are bounded; nothing that must survive a restart lives only in memory.
- Terms: the design's Appendix A, with no synonyms in code, docs or UI. The core: agent (the AI that talks), voice (the platform part that gives an agent a voice: the conversation and speech modules), conversation (sessions and their turns, in text), user context (loads and saves what an agent may know about a user; Go package `usercontext`), workspace (owns agents), user (the human talking to an agent), speech (speech-to-text and text-to-speech, and the module that runs them with the audio connection; never "voice").
- Module boundaries: speech imports conversation, never the reverse, so conversation stays text-only; user context imports none of the other modules and keeps its own tables; conversation calls user context's service directly, never its store or tables. One service, scaled by running more copies. Loosening a depguard list is a visible change in the PR that needs it.
- Inside each module, hexagonal (design D31): the core in the module folder holds the rules, declares its ports as small interfaces, and imports nothing outside but the modules it may use, `internal/access` and `internal/secret`; adapters live in subfolders (`http/`, `transport/webrtc/`, `stt/<vendor>/`, `store/postgres/`), and a new adapter folder falls under its core's depguard list until it gets one, as any other new package under `internal/` falls under one allowing only the standard library; `cmd/voice` wires them in.
- Vendor packages are imported only by their adapter, never by a module's core; a `cmd/` program that plays the browser for a check (`cmd/checkspeak`) may import Pion, as the other side of the connection. Every port has a fake adapter used by the core's tests from the port's first day. Each swap point (each speech stage, model access, storage) is an interface with the implementation chosen by configuration; an interface exists only for I/O: storage always (a core never touches the database directly), and a vendor or another service where at least two real implementations are planned; a fake doesn't count, and domain logic is called directly.
- Nothing may block scale-out: no conversation held in a server's memory between requests (any instance can serve any turn, and an audio connection can reconnect to any instance); workspace ID on every stored record and user ID on every record about a user, and every query filters by workspace, except the system's own sweeps (ending idle sessions, claiming and deleting background jobs), which find their rows by one condition across workspaces, the same for every workspace; ending and deleting read nothing out, and the claim reads out only the job it takes; the product key check finds a key by its hash, since the key names the workspace; IDs are UUIDv7, never a central counter; slow work runs as a background job, never inside a request; settings come from the environment.
- Every turn records per-stage timing; a change meant to make something faster is measured before and after.
- Comments explain why, sparingly, in their own words: never cite doc labels or section numbers, which get renumbered; cite an official standard or regulation (an RFC, a law) only, never another product, project or draft.

## Guardrails
- Never change a test just to make code pass. If a test looks wrong, stop and explain why; when a test change is justified, call it out explicitly in the summary and the PR.
- Never edit an item spec to match the code; propose the change instead.
- Change only what the item's spec covers; no drive-by refactors or reformatting of unrelated files. Work outside an item gets its own small PR.
- No new dependency without approval.
- Fix warnings rather than suppressing them; never bypass hooks (`--no-verify`) or weaken a check.
- Never merge a pull request and never delete a branch on GitHub; the developer merges after review, and merged branches stay.
- Directed work (an agreed spec or plan, the developer's review comments, an explicit request) goes all the way to an open pull request: commit, push and open it without asking again, then report. Work nobody directed is proposed first (the changes, the commit message, the files), and waits for an explicit go-ahead; a permission prompt is not the go-ahead.
- After two failed attempts at the same problem, stop and report rather than trying workarounds.
- Report evidence (commands and output), never just "tests pass", and say explicitly what was not run.

## Working agreements
- A task that isn't one plain command gets a script: one people run in `scripts/`, plumbing other scripts, the hooks or CI run in `scripts/lib/`, an agent-only task in its skill's folder (`.claude/skills/<name>/`); docs show the script, not the commands.
- Commits: small, saying why, in Conventional Commits form, `type(scope): description` (`feat`, `fix`, `test`, `refactor`, `docs`, `build`, `ci`, `chore`). One branch per pull request, named `type/short-name` with the PR's type; changes to the agent setup are `chore`. PR titles take the commit form; descriptions follow the template and read in a minute: Summary, Diagram, Key files, Notes, about 300 words; every change and every choice a reviewer could question ends with a bold **Why:** and a short phrase, and so does every number chosen (a deadline, a limit, a default: measured, derived from what, or a round guess and when it will be measured, also in the comment beside the constant); the diagram is plain ASCII.
- PRs are planned at 300 to 600 lines and never go past 800 (a hard limit), added plus removed, tests and docs included, lockfiles (`package-lock.json`, `go.sum`), sqlc's generated code and the schematic's files (`schematic/`, `cmd/classgen/`) not counted, docs-only work exempt; the spec estimates each PR, and one that would pass 800 is split by idea; one under 50 lines is considered for merging into a neighbouring PR on a related topic. A larger item is split by idea, each piece of code with the tests that prove it, by default in the order decisions and domain, happy path, one PR per failure scenario, chores.
- A PR that adds, changes or removes a service, a package, a port or its methods, an adapter, a connection between parts or a design decision updates the schematic in the same PR: the `schematic` skill, run before verifying; `go test` fails on a package, an import between the parts of voice or a port's method it doesn't show.
- Every gate is seen failing once before it is trusted: break it on purpose, watch it fail, then watch clean code pass.
- Review feeds the standards: when the developer's comment raises a rule rather than a one-off fix, fix the code, add the rule to `docs/reference/contributing.md` (and the extract here if agents need it on every edit) in the same pull request, and reply saying what changed. Never resolve a thread; the developer does after checking.

## Gotchas
- macOS filesystem is case-insensitive: `architecture.md` and `ARCHITECTURE.md` in one folder are the same file.
- Formatting is `golangci-lint fmt` (gofmt, goimports) through `scripts/format.sh`, used by the git hooks and the Claude hook. Never an IDE's own formatter.
- `golangci-lint fmt` exits 0 on a syntax error (a warning only); `scripts/format.sh <file>` runs `gofmt -e` first so it fails, and lint catches it at push.
- An import of a module missing from `go.mod` fails typecheck before depguard runs; to see a depguard list refuse a vendor package, add the module first (and remove it after).
